     Implementation Plan: Multiplayer Switch Player View (Spectator Mode)

     Overview

     Implement a "switch player view" functionality that allows players to 
     spectate other players' boards during multiplayer games. The feature
     will use a cycle button to toggle between viewing local player's board
     and other players' boards, with a header indicating whose board is
     being viewed and input disabled while spectating.

     Current Architecture Analysis

     Existing Multiplayer Sync System

     - SyncManager.cs: Handles serialization/deserialization of game state 
     via Firebase
     - PlacementActionData: Serialized shape placement data (shapeType, 
     buildingType, positionX, positionY, rotation, flipped, starsAwarded,
     timestamp)
     - BoardStateData: Contains list of BoardShapeData for compressed board 
     state
     - Firebase Structure: Placements stored at 
     games/{lobbyCode}/turn/{turnNumber}/placements/{playerId}
     - Event System: SyncManager.OnPlacementActionReceived event fires when 
     opponent placements are received

     Shape Management

     - ShapeManager.cs: Creates and manages shapes on local player's board
     - ShapeController.cs: Individual shape behavior (placement, rotation, 
     flip)
     - GameManager.cs: Main game loop, subscribes to multiplayer events
     - Current Limitation: Opponent placements are received via events but 
     only logged, not rendered visually

     Proposed Approach Evaluation

     The user's proposed approach is feasible and recommended:
     1. Store local player's placed shapes when switching to spectator mode
     2. Fetch shape placements from Firebase for target player
     3. Use ShapeManager to place those shapes visually
     4. Disable input with bool spectatingOtherPlayers flag
     5. Cycle back to local player: restore local shapes, enable input

     Advantages:
     - Reuses existing ShapeManager for shape creation
     - Leverages Firebase data already being synchronized
     - Minimal changes to core game logic
     - Clean separation between local and spectator states

     Alternative Considered (and rejected): Maintaining multiple board 
     visualizations simultaneously would require significant architectural
     changes and memory overhead.

     Implementation Plan

     Phase 1: Core Data Structures & State Management

     1.1 Create SpectatorManager.cs

     New singleton manager to handle spectator mode state and transitions.

     Location: /Assets/Scripts/Multiplayer/SpectatorManager.cs

     Responsibilities:
     - Track current view mode (local player vs spectating player)
     - Store/restore local player's placed shapes
     - Fetch and render opponent shapes from Firebase
     - Manage cycle through available players
     - Coordinate with GameManager for input disabling

     Key Properties:
     public bool IsSpectating { get; private set; }
     public string CurrentSpectatedPlayerId { get; private set; }
     private List<ShapeController> localPlayerShapesBackup;
     private Dictionary<string, List<BoardShapeData>> cachedOpponentBoards;

     1.2 Enhance SyncManager for Board State Retrieval

     Add method to fetch all placements for a specific player across all

     - Query Firebase for all placements under player's history
     - Aggregate into complete board state

     1.3 Add Spectator State to GameManager

     - Ensure spectator panel appears above other UI

     Phase 4: Input Management

     4.1 Disable Input During Spectator Mode

     Modify: /Assets/Scripts/GameManager.cs

     Update input handling methods:
     - OnPlaceShapeInput(): Check IsSpectatingOtherPlayers and return early
     - Dice selection: Disable via DiceUIManager.SetInteractable(false)
     - Shape manipulation: Disable rotate/flip/confirm buttons

     Phase 5: Firebase Integration & Performance

     5.1 Optimize Board State Fetching

     - Cache opponent board states in SpectatorManager.cachedOpponentBoards
     - Fetch incrementally as turns progress (listen to new placements)
     - Implement compression for large board states (use existing 
     BoardStateData compression)

     5.2 Handle Player Disconnections

     - Skip disconnected players in cycle
     - Show "Player disconnected" in header if viewing disconnected player
     - Auto-cycle to next available player

     Phase 6: Testing & Edge Cases

     6.1 Test Scenarios

     1. Single player mode: Spectator button should be hidden/disabled
     2. 2-player game: Cycle between local and opponent
     3. 8-player game: Cycle through all players in join order
     4. Mid-game join: Should fetch all historical placements
     5. Player disconnection during spectator mode

     6.2 Edge Cases

     - First turn (no placements yet): Show empty board
     - Water die placements: Ensure building type choice is preserved
     - Star visuals: Render stars on opponent shapes
     - Large board states: Performance testing with many shapes

     Critical Files to Modify

     1. /Assets/Scripts/Multiplayer/SyncManager.cs - Add board state 
     fetching
     2. /Assets/Scripts/GameManager.cs - Add spectator state properties
     3. /Assets/Scripts/ShapeManager.cs - Add shape storage/restoration
     4. /Assets/Scripts/UI/SpectatorUIManager.cs - New UI manager
     5. /Assets/Scripts/Multiplayer/SpectatorManager.cs - New core manager
     6. /Assets/Scripts/Core/ShapeSerializationHelper.cs - New utility
     7. Assets/InputSystem/PlayerInputs.inputactions - Add cycle action

     Dependencies & Order

     1. First: Create data structures and serialization (Phase 1, 2)
     2. Second: Implement core spectator logic (Phase 1, 2)
     3. Third: Build UI (Phase 3)
     4. Fourth: Integrate input (Phase 4)
     5. Fifth: Optimize Firebase (Phase 5)

     Success Criteria

     1. Player can cycle through all opponents' boards with a button
     2. Header clearly indicates which player's board is being viewed
     3. Input is disabled while spectating (no placement, dice selection, 
     manipulation)
     4. Shapes render correctly with proper colors, rotations, and positions
     5. Performance: Switching views should be smooth (< 1 second)
     6. Memory: Caching prevents repeated Firebase queries
     7. Edge cases handled gracefully (disconnections, empty boards)

     Notes

     - The existing BoardShapeData structure already contains all needed 
     information (shapeType, buildingType, position, rotation, flipped,
     turnPlaced)
     - Star visuals need to be recreated when rendering opponent shapes 
     (starsAwarded field in PlacementActionData)
     - Consider adding visual distinction between local and opponent shapes 
     (e.g., slight transparency for opponent shapes)
     - Multiplayer turn coordination should continue working (spectator mode
      doesn't affect turn completion tracking)
